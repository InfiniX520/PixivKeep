# 下一轮开发指导：先修证据边界，再接入功能

起点固定 `031627c64eb2aac5605b05a21a47a7c0b3c5fef2`。本轮只做审计和导航，产品没有修改。先读 [发现](FINDINGS.md)和 [执行结果](evidence/results.json)，不要用旧日志中的“全关闭”代替新发现。

## 0. 执行方式与交付纪律

1. 从审计分支新建修复分支/隔离 worktree。日常 `4ba891e` 保持，五个脏树原位保留。禁止用清空 .runtime 或重置 worktree 来获得干净环境。
2. 主智能体先读核心文件、确认下述契约，输出对齐方案并结束该轮；用户确认后再按工作区 AGENTS 用继承上下文的 fork。每条提示必须原样含 AGENTS 规定的质量/预算/安全句。不能无上下文分发业务代码。
3. 新反例作为独立测试带入并冻结红基线。不得删断言、改成 xfail 或以 mock 全业务方法的测试替换；若契约确需改变，提交证据和修订理由。
4. 不增加数据迁移或环境安装作为顺手改动。当前问题能先用合成资料修复。成熟解码组件可做单列选型，但未完成核验/安装流程不能直接装入共用环境。
5. 文件所有权按下面工作包划分；`library_maintenance.py` 和 `quality_check.py` 不交给两人同时修改。主集成者串行接入跨包接口。进度按契约、代码、整链验收、UI接线、生产验收五种状态分别记录。

| 契约 | 必须写清 | 拒绝的捷径 |

## S1：工作区写入与清理（UX-01 + WR-04，单一所有者，最高优先）

负责：`workspace_ownership.py`、`library_maintenance.py` 中建立/复制/SQLite/清理生命周期，以及对应测试。先完成它，再由集成者接入质量 CLI 出口改动。

实施步骤：

1. 为已创建对象建立不可覆盖的 ownership record。将“独占创建”“验证已知对象”“观察外来对象”分成不同 API；record 不得悄悄把旧 claim 换成另一个身份。
2. 复制接口消费已拥有的写入句柄或等效能力对象。验证必须在 truncate/write 之前；验证失败不写一字节。处理根/父目录替换、硬链接、reparse 和身份不可用。Windows 使用何种句柄共享标志、是否允许路径替换要有实测，不能只写注释。
3. 清点 `_copy_and_hash`、`_copy_file`、在线 SQLite backup、manifest 写入和 restore-check 的所有目标，不只修此次测试入口。读取源稳定性与写入目标所有权是两条独立保证。
4. 对 SQLite sidecar 明确如何证明归属。如果无法拿到创建证据，宁可保留临时目录并报告具体原因，也不把出现的同名文件收养。不要预创建会破坏 SQLite 行为的文件来骗测试。
5. 一次调用保存主结果与 cleanup 结果。异常路径包括 claim/record/fstat/open/SQLite/discard，各自有 typed 回执；finally 不能再抛异常覆盖前因。

验收矩阵必须含：正常备份/verify/restore-check；claim 后替换；父目录替换；同名陌生 sidecar；自己创建的 sidecar；lstat 权限失败；身份未知；复制中断；主失败同时清理失败；保留内容与原文件 SHA256。两条 UX-01 + WR-04 独立反例应转绿；上一轮 14 条及归档工具 23 条保持绿。

**不可接受的修法**：只是捕获全部异常返回 ok=False，但外部 sentinel 已被写坏；或只保住 sentinel，却再也不能正常 verify；或把所有保留目录都后台删掉。既验证错误返回，也验证真实磁盘前后内容。

## S2：质量引擎与受控读取（UX-02/03/04，同一所有者）

负责：`quality_check.py`、`png_decode.py`、`decode_limits.py`、`decoder_registry.py`、`quality_evidence.py`。CLI 最终组合由集成者在 S1 后串行合并到 `library_maintenance.py`。

1. 先修 budget/stop 的全程作用域和同版本读取，再改解码语义。尽量复用现有有界观察机制，减少无依据的全文件重复读取；性能收益必须以真实 I/O 字节数说明。
2. 质量结果记录被检查内容身份与当前路径稳定性；终态 changed/unknown 不能成功。前后长度/摘要/句柄证据各有意义，明确观察结束时刻，不承诺回执返回后的文件状态。
3. transport 只在可信预期长度和本次实际长度相等时为 length_matched；错长度、无预期、无法读取三个情况分别测试。也核对 expected_media_type 传播。
4. PNG 索引色按 PLTE 项数检查解码像素。测试 1/2/4/8 位深，行末填充位不作像素；每个 Adam7 pass、首行滤波和前一行生命周期必须独立。不要只在 8 位非交错分支加 if。
5. 有效图矩阵至少含五种 filter、合理位深/色彩组合、多个 IDAT、Adam7；无效矩阵含越界索引、缺/重复/错误 PLTE、截断、CRC、无效 filter、非法关键块、超限/取消、APNG 不支持。结构层已经拒绝的格式要在公开 CLI 整链确认，不能把独立 decoder 的职责和公开入口混为一谈。
6. 对成熟解码器差分测试时固定工具/版本和输入来源。宽容显示结果不等于严格规范校验；严格校验也不要求把所有格式都自研一遍。保持 JPEG/GIF/WebP capability_unavailable 的诚实状态，直至确有组件验收。

验收包含 UX-02/03/04 全部用例、正常 PNG 对照、预停止零完整哈希、前/中/后阶段取消、有界长行取消延迟、预算实际消耗、文件被换后的非零退出码。不要拿“decode 阶段 1ms”掩盖前面哈希花了几分钟。

## S3：覆盖事实与单位（UX-05/06，独立文件组）

负责：`follow_facts.py`、`follow_coverage_state.py`、`follow_coverage_counts.py`、`follow_coverage.py`、`follow_coverage_text.py`。先不改下载任务状态机或真实库 schema。

## 并行与集成顺序

S0 完成且用户确认后可分 **S1、S2、S3/S4** 独立模块（按实际可用并发槽；一个执行者可顺序做 S3 再 S4）。S1 与 S2 不同时写 `library_maintenance.py`；CLI接线由主集成者串行做。测试作者可写独立跨模块用例但不得改产品语义替实施“解释成通过”。

合并按 S1 → S2 引擎与CLI → S3 → S4 → S5 小修；每个提交先跑所属包与边界测试，再跑一次整套。主智能体检查类型/编译/全量后，按 AGENTS 做只读 fork 审 diff；问题发回原上下文，不另起空白模型。仅修独立引擎不要求顺便部署、升级环境或改业务数据。

## 每批必须留下的接续材料

一个批次目录、一个 README、一个固定产品 SHA；红基线、针对测试、全量和首轮失败分别保留，不覆盖。产品报告只收摘要，原始日志/本机路径/DB 在 .runtime。当前 README、docs/README、IMPLEMENTATION、TASK_PLAN、LOG 同步同一版本状态；历史报告不改日期或原结论。
